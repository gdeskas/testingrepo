1. INCIDENT SUMMARY
───────────────────────────────────────────────────────────────
On 17 March 2026 at 09:14 UTC, the primary PostgreSQL cluster
(prod-db-eu-west-1) entered a degraded state due to a runaway
query triggered by the newly deployed recommendation engine
(v2.4.0). Connection pool exhaustion cascaded to the API layer,
resulting in HTTP 503 errors for approximately 68% of requests.

Duration:       09:14 – 10:47 UTC (93 minutes)
Severity:       SEV-1 (customer-facing, revenue-impacting)
Affected users: ~42,000 (EU region)
Revenue impact: Estimated £18,200 in lost transactions
SLA breach:     Yes — monthly uptime dropped to 99.84%
                (target 99.95%)

3. ROOT CAUSE
───────────────────────────────────────────────────────────────
The recommendation engine v2.4.0 introduced a new "similar
items" query using a recursive CTE that, for certain product
categories with circular tag relationships, entered an
unbounded recursion. The query lacked a MAXDEPTH limit and
no query timeout was configured at the application layer.

Contributing factors:
  • Staging database had only 2% of production data volume —
    the pathological case was not triggered in testing
  • No per-query timeout in the SQLAlchemy connection config
  • PgBouncer max_client_conn was set too high (500),
    allowing the DB to accept connections beyond safe capacity
  • Canary deployment metrics checked API latency but not
    DB connection pool saturation

───────────────────────────────────────────────────────────────
5. LESSONS LEARNED
───────────────────────────────────────────────────────────────
• Query timeouts should be mandatory in all services — not
  optional. Adding to our service template.
• Staging environments must have representative data volumes
  for performance-sensitive features.
• Rollback alone is insufficient when the damage is in-flight
  database queries — we need a "kill queries" runbook step.
